# CaddieOS — Product Audit & Changes

Senior-engineer pass focused on the three things you asked for: **trustworthy data
in, accurate club intelligence, and a real onboarding "wow."** Nothing speculative
was added — every change below serves accuracy, data reliability, or ease of use.

The app is a single-file React artifact (`src/CaddieOS.jsx`, uses the Claude
`window.storage` API). The baseline you provided is committed verbatim as the first
commit so every change is reviewable in `git log`.

---

## 1. Bugs found & fixed (accuracy / reliability)

### 🔴 Course tab crashed on Patrick Farms
The Course tab rendered `h.plan.map(...)`, but **every Patrick Farms hole has no
`.plan`** — its plans are generated by the engine. Opening Patrick Farms in the
Course tab threw `Cannot read properties of undefined (reading 'map')` and blanked
the tab. Fixed to use the existing `getPlan(h)` helper (which generates a plan when
one isn't hand-written), matching how the rest of the file already works.

### 🔴 Reliability stats were inflated by the "ON PLAN" button
"ON PLAN" logs `gain = expected carry`, so its distance error is **exactly 0**.
Those synthetic taps were being averaged into every club's dispersion, average, and
hot/cold detection — pulling each club artificially toward "perfectly on your
number." That makes the caddie *look* more reliable than it is, which is the exact
opposite of earning a golfer's trust.

Fix: ON PLAN shots are now tagged `p:1` (estimated, not measured) and excluded from
the dispersion (`disp`), confidence (`conf`), club report, and live cold/hot
detector. Measured outcomes (ON GREEN, and REPLAN with real yards-left) still count.
Older saved shots lack the tag and are treated as before — no data migration needed.

### 🟡 Club report was hardcoded to six clubs
The Trends → Club report iterated a fixed list `["52","PW","9i","7i","8i","3W"]`, so
any club a golfer added (or imported) would never appear. Now it reports the actual
bag (`["52", ...your carries]`).

## 2. The headline feature: launch-monitor upload → auto-profile

This is the "plug in my data and my caddie learned" moment. It lives in the **ME**
tab and is linked from the empty **PLAY** screen for first-run onboarding.

**Flow:** drag-and-drop (or browse) a `.csv` → we do everything else → confirmation
screen → one tap to learn your game.

What it does, all automatic:
- **Format detection** — finds the header row even when the export has a title line
  above it, and maps columns (`Club`, `Carry`, `Total`, `Ball Speed`, `Smash`,
  `Spin`, `Side`, `Date`) by name. The golfer never picks a format.
- **Club recognition** — `7 Iron`, `7I`, `7i`, `PW`, `54`, `54°`, `Driver`, `3W`,
  `gap wedge` all resolve to one canonical club. Unrecognized labels are reported,
  not silently mislabeled.
- **Bad-data filtering** — drops blanks, zero/negative carries, and physically
  impossible readings (carry > 400y, ball speed > 240 mph, smash outside 0.5–1.7).
- **Mishit filtering** — within each club, drops topped/fat strikes below 55% of that
  club's median so one chunked 7-iron doesn't drag your number down.
- **Duplicate detection** — identical (timestamp + club + carry + ball speed) rows
  are de-duped, so re-importing the same file is safe.
- **Confirmation screen** — *"We found 86 shots"* + a per-club table (shots →
  **stock carry**, the range it plays, ±dispersion, short-miss %, NEW vs UPDATE) and
  a summary of everything filtered out. Nothing is written until you confirm.
- **Derives your numbers** — stock carry = **robust median** (resistant to outliers),
  plus a conservative "count-on-it" 20th–80th percentile band. These write straight
  into the profile the decision engine already runs on. The 52° scoring wedge is
  routed into the app's `w52` full-smooth window instead of a plain carry.

### Left/right miss (SC4 Pro side tracing + spin axis)
SC4 Pro exports include **side-carry tracing** and **spin axis (left/right spin)**, so
the importer learns each club's **miss side** too. It prefers measured offline yards
(tracing) and falls back to spin-axis direction (curve) when only that is present.
Per club we compute a dominant miss side and how often (e.g. *"misses right 68%"*),
shown in the confirmation screen, the Caddie Profile, and the club report. Right is
positive, left is negative; the parser handles `R12` / `L8` / `-8` / `+3` codings.
If a file has neither side nor axis, we simply omit it — we never invent a direction.

## 3. The "wow": Caddie Profile

After an import, the ME tab shows **"{Name}'s Caddie Profile"** built from the real
shots: longest club, best scoring club (tightest dispersion), least-trusted club,
a smart-target line, a short-miss warning, and a full bag readout with each club's
carry, the range it plays, sample size, and a reliability word (rock-solid →
inconsistent). This is the "here is your player profile" deliverable.

## Verification
- Importer logic proven in Node against realistic SC4 Pro exports — column
  detection, title-row skipping, club recognition across messy labels,
  mishit/impossible/duplicate/blank filtering, robust median carries, dispersion,
  52°-wedge routing, and signed left/right parsing (tracing + spin-axis fallback).
  Suites run against the code as actually inlined in `CaddieOS.jsx`. All pass.
- **End-to-end browser test** (headless Chromium on `caddie.html`): app renders with
  no console/page errors; uploading a sample SC4 CSV shows the "We found N shots"
  confirmation with the correct side-miss, and IMPORT produces the Caddie Profile.
  This caught a real bundling bug — `CaddieOS.jsx` never imports `React`, so the
  classic JSX transform left `React` undefined and the page rendered blank; fixed by
  building with esbuild's automatic JSX runtime.

## `caddie.html` (runnable build)
Fully self-contained — React and the app are bundled and inlined (no CDN, no runtime
transpile, works offline). `window.storage` is shimmed over `localStorage`.
Regenerate with `npm run build` after editing `src/CaddieOS.jsx`.
